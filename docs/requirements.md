# NovaParty 需求草案

状态：讨论稿 v0.1。本文记录已确认的产品方向；建议方案和待定事项不视为已确认需求。

已开始实现桌面验证原型，实测范围与限制见 [验证记录](validation.md)。原型接口见 [SDK 契约](sdk.md) 和 [通信协议](protocol.md)。

## 1. 产品目标

基于 Godot 构建无中心服务器的多人游戏平台。每台设备都是完整客户端，可以加载游戏 Mod、创建或加入房间、参与对局。开发者可以使用 AI 编写游戏规则、界面和资源，打包后导入客户端运行。

首版聚焦棋牌，同时为后续其他类型的联机游戏保留扩展空间。实时对战与格斗游戏不属于首版交付范围，不要求沿用棋牌的同步方式。

## 2. 已确认需求

| 项目 | 要求 |
| --- | --- |
| 引擎 | Godot |
| 目标设备 | Android 手机、iPhone、安卓电视 |
| 客户端形态 | 每台设备都是完整客户端，不采用电视显示、手机仅作控制器的基础模型 |
| 网络目标 | 无中心服务器，支持离线联机；期望包含局域网和蓝牙 |
| 玩家身份 | 具备玩家标识，可显示昵称或代号 |
| 首版游戏范围 | 棋类，以及麻将、扑克等包含隐藏信息的牌类 |
| 扩展方式 | 游戏以 Mod 形式提供，包含自定义逻辑和资源，打包后加载执行 |
| Mod 信任模型 | 首版加载可信 Mod |
| 开发支持 | 优先设计通信 SDK，提供 Skill 或其他 AI 可用的开发说明 |

“支持棋牌”指平台具备承载这些游戏的能力，不代表首版实现所有棋类、麻将和扑克玩法。

## 3. 建议的首版交付范围

以下为建议基线，需在原型验证后确定。

- 三类目标设备均可独立加载游戏、创建房间和加入对局。
- 局域网联机作为首版必备能力，蓝牙先做可行性验证，交付阶段单独确定。
- 使用本地玩家档案，无需注册账号或访问中心服务。
- 房主设备主持对局并运行权威规则。
- 普通参与者可在房间仍存在时断线重连；首版不自动迁移房主。
- 提供五子棋和一种具体扑克玩法作为参考 Mod，分别验证公开状态与私有状态。
- 为麻将提供所需的私有信息和多人操作处理能力；具体麻将玩法与首发时间待定。
- 提供 Mod 模板、SDK 文档、AI Skill、打包与校验工具。

首版不包含公开匹配服务、中心账号、陌生人 Mod 沙箱、Mod 依赖系统和竞技级防作弊。

## 4. 核心用户流程

1. 首次启动，生成本地玩家标识，设置昵称。
2. 导入并加载可信游戏包。
3. 创建房间，选择游戏与规则配置；其他设备发现房间或通过手动方式连接。
4. 加入时检查协议及游戏包兼容性，不兼容时说明原因。
5. 玩家入座、准备，由房主开始对局。
6. 玩家提交操作，房主校验并推进规则，各设备更新自己的可见状态。
7. 参与者掉线后尝试恢复身份、座位与当前可见状态。
8. 对局结束，显示结果；按游戏能力保存记录。

## 5. 平台、SDK 与 Mod 的边界

### 平台客户端

负责本地玩家档案、Mod 安装和加载、房间入口、连接状态、通用输入、存储与错误提示。

手机支持触屏；电视支持遥控器，手柄支持范围待定。游戏包应声明支持的输入方式，平台应在进入游戏前识别不支持的设备组合。

### 联机 SDK

负责连接抽象、房间与玩家生命周期、座位、消息封装、版本检查、操作顺序、确认与去重、快照和重连。

SDK 不内置“落子”“吃碰杠”等具体游戏行为。Mod 声明操作类型及数据结构，SDK 传输操作，规则逻辑判断其含义与合法性。

传输层与游戏同步方式分别扩展。局域网与蓝牙不应进入游戏规则；未来实时游戏可以使用其他同步模式，而不必复用棋牌的状态推进机制。

### 游戏 Mod

负责规则配置、初始状态、操作定义与校验、状态推进、玩家可见状态、胜负结算，以及界面、动画、音效等资源。

规则与表现分离。表现层读取本机可见状态、提交操作，不直接修改权威状态。相同状态与操作应能得到可重现的规则结果；随机行为需通过明确、可记录的规则机制处理。

## 6. 身份与房间模型

建议区分以下对象：

- 玩家 ID：本地档案的稳定标识，不随昵称变化。
- 显示信息：昵称、短代号；头像为可选能力。
- 连接会话：本次连接的临时标识，不等同于玩家身份。
- 座位：本局游戏中的参与位置，与连接生命周期分离。

本地身份用于识别与恢复，不作为实名认证或防冒用保证。重连必须证明持有原会话的恢复凭据，不能仅凭提交相同玩家 ID 接管座位。具体凭据方案在协议设计阶段确定。

房主设备拥有对局权威。房主退出、后台挂起或连接中断时，应明确显示对局状态；恢复、超时与结束策略需进一步确定。

## 7. 状态可见性与棋牌同步

| 状态类别 | 示例 | 可见范围 |
| --- | --- | --- |
| 公共状态 | 棋盘、弃牌、轮次、剩余牌数 | 房间内有权查看对局的设备 |
| 玩家私有状态 | 自己的手牌、私有可执行操作 | 对应玩家 |
| 房主内部状态 | 完整牌堆、全部手牌、随机数状态 | 房主规则逻辑 |

建议流程：玩家提交操作 → 房主验证身份、权限和对局版本 → Mod 校验规则并推进状态 → 为每位接收者生成可见结果 → SDK 分别发送 → 客户端更新表现。

私有信息必须在发送前过滤，不能发送完整状态再由界面隐藏。快照、错误信息和对局记录也应遵守可见性边界。

协议需要能够处理重复操作、过期操作、乱序到达和重复连接。玩家操作被接受或拒绝时，应返回可关联到原请求的结果。

麻将等游戏可能允许多位玩家响应同一个事件。规则接口需支持响应窗口、优先级、截止条件与统一结算，不能只假设“每个时刻只有一个玩家可以行动”。具体优先级由玩法定义。

房主运行完整规则，因此房主设备可接触完整信息。首版接受此信任模型，不承诺防止恶意房主作弊。

## 8. Mod 包与 AI 开发体验

建议游戏包声明：游戏标识、版本、SDK 兼容范围、规则入口、表现入口、资源清单、输入能力，以及规则配置结构。加入房间时检查内容指纹，避免版本名称相同但实际内容不同。

首版建议双方提前安装相同游戏包；房间内自动传包暂不列入必备范围。

跨平台自定义逻辑的执行形式、资源格式、Godot 版本与加载机制均需原型验证后确定。可信 Mod 不等同于不需要版本、结构和资源引用校验。

AI 开发交付物包括：

- SDK 接口和机器可读的数据结构说明。
- 可直接运行的游戏模板。
- 五子棋与私有手牌游戏示例。
- 指导 AI 实现规则、表现、验证与打包的 Skill。
- 能返回清晰错误的包校验工具和多人规则模拟工具。

目标流程：描述玩法 → AI 创建或修改 Mod → 校验规则与包结构 → 打包 → 导入客户端 → 多设备试玩。

## 9. 优先技术原型

### 原型 A：跨平台加载 Mod

在 Android 手机、iPhone、安卓电视上加载同一份测试游戏包，执行自定义规则、展示资源并响应输入。

需验证目标分发渠道下的可交付性、加载机制、版本兼容、资源路径与生命周期。若同一包无法直接跨平台使用，应明确是否允许由同一源码生成各平台包。

通过条件：记录可复现的构建和加载步骤，列出实际支持范围及限制。此原型通过前，不固定最终包格式与脚本执行方式。

### 原型 B：跨设备局域网对局

验证 Android、iPhone、安卓电视之间创建和加入房间、操作同步、私有状态分发及参与者重连。覆盖应用进入后台、设备休眠和网络切换后的提示与恢复行为。

通过条件：完成一局公开棋盘游戏和一局隐藏手牌测试，客户端收到的信息符合其权限，恢复后座位与状态一致，重复操作不会重复执行。

### 原型 C：蓝牙可行性

列出各目标平台组合和实际设备，验证发现、连接、消息传输及所需权限。根据结果决定正式支持的组合与交付阶段，不预先承诺全平台互通。

## 10. 首版验收目标

- 无互联网、无中心服务时，受支持的设备组合可以在同一局域网完成对局。
- 每台设备均可独立操作，昵称或代号可辨认，身份与座位不会因普通重连丢失。
- 不同游戏包或协议不兼容时，进入对局前给出明确提示。
- 非法、重复与过期操作不会破坏对局状态。
- 普通客户端不会收到其他玩家的手牌或房主内部状态。
- 手机与电视均能完成选中、确认、取消等游戏必需操作。
- 开发者或 AI 按文档可制作一个新 Mod，通过校验并导入运行，无需修改平台核心代码。

## 11. 待定事项

1. iPhone 的目标分发方式，以及是否要求安装后直接导入含新逻辑的游戏包。
2. 首发具体扑克、麻将玩法与玩家人数。
3. 参考游戏与 SDK 支持能力的首版交付边界。
4. 蓝牙首版是否必须交付，以及必须支持的平台组合。
5. 电视必需支持的遥控器、手柄及设备范围。
6. 房主失联、玩家离席、超时、托管与恢复策略。
7. 是否支持观战，以及回放如何处理私有信息与查看权限。
8. 游戏包导入渠道、本地身份备份和跨设备迁移需求。

建议下一步先完成两个技术原型，再确定 SDK 接口、协议结构与 Mod 包规范。
